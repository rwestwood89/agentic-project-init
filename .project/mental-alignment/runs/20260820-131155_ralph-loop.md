# Ralph loop — how it works and how you drive it

## 1. Ralph is two programs, and you run them at different times

Get this straight first, because "the ralph loop" names only the second one.

- **`ralph-init.sh`** — a one-shot scaffolder, run once by hand from inside a git repo. Seven Claude
  calls turn a concept file into a project skeleton in a new git worktree. No application code.
- **`loop.sh`** — the actual Ralph loop. *Generated by* init, lands inside the worktree. You `cd`
  there and run it; it calls `claude -p` in a `while true` until you cap it or kill it. This writes
  the code.

So "using the ralph loop" is: write a concept file → run init once → review what it generated → run
the loop in plan mode → review the plan → run the loop in build mode.

*Provenance: code, directly — `claude-pack/scripts/ralph-init.sh:87` and the `loop.sh` heredoc at
`:817-873`. Visual: two boxes with a handoff arrow, "run once by hand" and "runs until stopped."
Everything below hangs off that split.*

## 2. The whole thing is driven by one input: a concept file about outcomes

`ralph-init.sh <project_name> <concept_file>` is the entire interface. The concept file is markdown
describing **outcomes** — what the system should do, not how. Everything downstream derives from it,
so its quality sets the ceiling for the run.

Two preconditions that stop you cold: you must be inside a git repository (`ralph-init.sh:172`), and
the output worktree must not already exist unless you pass `--resume` (`:200-217`).

Output goes to a **sibling directory** of your repo, not a subdirectory —
`../<repo-basename>_<project_name>`, on branch `ralph/<project_name>` (`:178-182`). The symlink is
installed, so the live invocation is `~/.claude/scripts/ralph-init.sh <name> <concept>`.

*Provenance: code plus README.md:159-187. I verified the `~/.claude/scripts/ralph-init.sh` symlink
exists, so it is installed right now. Visual: a "before you run it" checklist plus a small path
diagram showing the sibling worktree beside the repo.*

## 3. Init builds a ladder of artifacts, each one the input to the next

Ten labeled steps, seven of them Claude calls. The interesting part is the shape: it is a
compression ladder, and the design phase deliberately triples up.

| Step | Output | Model used |
|---|---|---|
| 3 | `DESIGN_v1.md` from the concept | `--design-model` |
| 3b | `DESIGN_REVIEW.md` — a critical review of v1 against six named dimensions | `--design-model` |
| 3c | `DESIGN.md` — v1 refined against the review, with a "Changes from V1" section | `--design-model` |
| 4 | `specs/*.md` — one file per topic of concern, from `DESIGN.md` | `--model` |
| 5 | `AGENTS.md` — the operational guide, ~60 lines, loaded every iteration | `--model` |
| 6 | `PROMPT_plan.md` — the planning-mode prompt | `--model` |
| 7 | `PROMPT_build.md` — the build-mode prompt | `--model` |
| 10 | `loop.sh`, `pyproject.toml`, `src/<pkg>/`, `tests/`, `.gitignore`, first commit | none (heredocs) |

Two things worth holding onto:

- **The design→review→refine chain is why `--design-model` exists separately.** Steps 3, 3b, and 3c
  are the only ones that use it. Opus there, sonnet elsewhere is the intended shape
  (`ralph-init.sh:24-25`; review dimensions at `:361-411`).
- **Steps 6 and 7 generate prompts, not code.** Ralph writes its own loop prompts from a
  meta-prompt, so the wording of `PROMPT_build.md` differs run to run. If the loop misbehaves, those
  two files are the first place to look and the cheapest place to hand-edit.

*Provenance: code, step by step — `claude_run` calls at `ralph-init.sh:321, 489, 555, 627, 691, 741,
796`. Visual: a vertical ladder, concept at top, each artifact feeding the next, the three design
passes visibly nested as one stage.*

## 4. The loop's trick: state lives in files, context is thrown away every iteration

`loop.sh` is 40 lines and does almost nothing (`ralph-init.sh:817-873`). Each pass it pipes one
prompt file into a fresh `claude -p`, then pushes the branch. No conversation carries over. That is
the whole design — continuity comes from files the agent reads and rewrites:

- `specs/*` — the requirements. Read every iteration, never rewritten.
- `IMPLEMENTATION_PLAN.md` — the task queue and the memory. **Created by plan mode, not by init.**
- `AGENTS.md` — how to build, test, and lint. Kept tiny because it costs context every iteration.
- `src/` and git history — what is actually built.

Two modes, selected by the first argument:

- **Plan** (`./loop.sh plan 3`) uses `PROMPT_plan.md`: study specs and existing code, gap-analyze,
  write or update `IMPLEMENTATION_PLAN.md`. No implementation, no commits.
- **Build** (`./loop.sh 10`) uses `PROMPT_build.md`: pick the most important remaining task,
  implement exactly one, run pytest/mypy/ruff, update the plan file, commit.

Sharp edge in the argument parsing: **a bare `./loop.sh` or `./loop.sh plan` means zero, and zero
means run forever.** Always pass a number (`ralph-init.sh:819-833`).

*Provenance: the `loop.sh` heredoc is verbatim code; the two modes' behavior is what the meta-prompts
ask for (`:713-733`, `:759-790`), unconfirmed against a generated pair. Visual: a cycle diagram with
the file set drawn outside the loop as persistent state and a slashed arrow for discarded context.*

## 5. Quality control is "backpressure," and it is mostly in the prompts

Ralph has no reviewer stage. What keeps it honest is that every task is tied to a command that can
fail, plus explicit guardrails in the build prompt.

- **Backpressure** = the validation commands in `AGENTS.md` (pytest, mypy, ruff). The plan prompt
  requires each task to note what backpressure verifies it (`ralph-init.sh:728`); the AGENTS.md
  prompt calls the validation section "the backpressure" (`:673`).
- **Task sizing** — one task per iteration, roughly five files max (`:726`).
- **The 9s guardrails** — a list where more 9s means more critical (`:775-784`, full text in the
  appendix). The load-bearing ones: implement completely, no placeholders or stubs; single sources
  of truth, no migration shims; keep `IMPLEMENTATION_PLAN.md` current; and *don't assume something
  isn't implemented — search first*.

*Provenance: the meta-prompts, verbatim. Whether the generated prompts preserve all of it is
unverified — this is the layer most likely to drift between runs. Visual: a "what stops a bad
iteration" flow with the three checks as gates.*

## 6. What will actually bite you

Ordered by how likely you are to hit it.

1. **The scaffold is Python-only, and hardcoded.** `pyproject.toml` (UV, pytest, ruff, mypy
   `strict`), `src/<pkg>/`, `tests/conftest.py` (`ralph-init.sh:875-925`). Three prompts also state
   it — the AGENTS.md one (`:662-665`) and both loop prompts (`:733`, `:788`). Anything else means
   hand-editing the scaffold *and* prompt text inside the script. The design and spec prompts are
   language-neutral, so the top of the ladder ports; the bottom does not.
2. **`loop.sh` hardcodes `--model sonnet`** and ignores `RALPH_MODEL` (`:864`). The env vars only
   affect init.
3. **The loop pushes to `origin` every iteration.** No remote, no permission, or a protected branch
   means a failed push each pass. It won't stop the loop — `loop.sh` has no `set -e` — but it is
   noise, and the resume-from-git story quietly depends on it (`:867-868`).
4. **Nothing detects "done."** The loop stops on your iteration cap or your Ctrl-C. Nothing else.
5. **Both scripts run `--dangerously-skip-permissions`** (`:95`, `:861`) — unattended, fully
   permissioned code execution. Fine in a throwaway worktree; worth knowing that's the deal.
6. **A stale copy of the script exists** at `.project/active/add-ralph/ralph-init.sh` (851 lines,
   pre-resilience). The canonical one is `claude-pack/scripts/ralph-init.sh` (1007 lines).

*Provenance: all code observation, except item 6 from git history (`08b4db8` moved it, `c0a8428`
changed the write mechanism). Visual: a ranked list — no diagram earns its place here.*

## The recipe, condensed

```bash
cd ~/my-repo                                                  # 1. concept file describes OUTCOMES
~/.claude/scripts/ralph-init.sh my-thing ./CONCEPT.md --design-model opus
cd ../my-repo_my-thing && uv sync --extra dev                 # 2. review DESIGN chain, then specs/
./loop.sh plan 2                                              # 3. writes IMPLEMENTATION_PLAN.md
                                                              # 4. read it; fix by hand if wrong
./loop.sh 5                                                   # 5. build; watch the first two
```

If init dies partway, re-run the identical command with `--resume`. It skips any step whose output
file already exists and is non-empty, and enters the existing worktree instead of erroring
(`ralph-init.sh:58-84`, `:200-217`). There is also a `ralph-init.log` in the worktree with
`START`/`END`/`SKIP` lines per step (`ralph-init.sh:227-233`); it is gitignored.

# Judgment

## Concerns

- **The generated layer is unverified, and it is the layer you depend on.** `PROMPT_plan.md`,
  `PROMPT_build.md`, and `AGENTS.md` are all model output from meta-prompts. Everything I said in
  sections 4 and 5 about loop behavior describes what the meta-prompts *ask for*. A weak generated
  `PROMPT_build.md` would degrade every subsequent iteration silently, and nothing in the script
  checks its content — only that the file is non-empty.
- **Infinite default on the loop is a real trap**, not a nitpick. `./loop.sh` with no argument runs
  unattended, fully permissioned Claude in a `while true` that commits and pushes each pass.
- **The Python hardcoding is deeper than the scaffold.** It is baked into six of the seven prompts,
  so changing target language means editing prompt text inside the script, not swapping a template.
- **Both Ralph work items sit in `.project/active/` while reporting complete**, and
  `ralph-resilience/plan.md` says "In Progress" in its header and "Complete" at the bottom. The
  2026-08-17 status report already flagged this (`.project/reports/2026-08-17-0959-status-report.md:79-80`).
  It cost me time deciding which artifacts were current. Not a Ralph bug, a tracking one.

## Unresolved uncertainty

- **Has this ever been run end to end since the tool-writes change?** Commit `c0a8428` switched
  generation from "capture Claude's stdout and parse it with AWK" to "let Claude write files
  directly with tools." That invalidates a chunk of the resilience design, which is built around
  validating captured stdout. I found no generated Ralph worktree, no `ralph-init.log`, and no
  `ralph/*` branch to confirm a real run happened after that change.
- **Does the spec step reliably produce multiple files?** Under stdout-capture there was an AWK
  parser splitting one blob into files. Now the prompt just asks Claude to write into `specs/`, and
  the only check is `find specs -name '*.md' -size +0c | wc -l` being greater than zero
  (`ralph-init.sh:630-637`). One spec file passes that check as happily as eight.
- **How Ralph relates to your `/_my_*` pipeline.** Nothing in the repo positions them against each
  other. They overlap heavily — both go concept → design → review → spec → plan → implement. Ralph
  is the unattended version with no human gates. `workflow-orchestrator` cites Ralph only as prior
  art for headless `claude -p`, not as something to unify with. Worth deciding deliberately rather
  than by accident.

## Disagreements between sources

- **`ralph-resilience/design.md` describes functions that no longer exist.** It is written against
  `claude_generate` and `claude_generate_design`, and its centerpiece is a tolerant AWK regex for
  parsing fenced spec blocks out of stdout. The current script has a single `claude_run` and no AWK
  at all. Trust the script; treat that design as a historical record.
- **Step numbering is internally inconsistent.** Code comments say "Step 4: Generate Specs" while
  the user-facing log for the same block says "Step 6/10" (`ralph-init.sh:567-575`). Harmless, but
  it makes the log confusing to follow against the source.
- **Claude-call count.** `ralph-resilience/spec.md` says "~5 times per run." I counted seven
  `claude_run` invocations in the current script. The spec predates the third design pass.

## Suggested spot checks

- `./loop.sh` argument handling: read `ralph-init.sh:819-833` and confirm for yourself that a bare
  invocation yields `MAX_ITERATIONS=0` and an unbounded `while true`.
- Do a cheap real run on a throwaway concept file, then read the generated `PROMPT_build.md` and
  `PROMPT_plan.md`. That is the only way to close the biggest gap in this synthesis.
- Check whether `git push origin <branch>` succeeds from a fresh Ralph worktree in your setup
  before starting a long build run.
- `git ls-files -s claude-pack/scripts/ralph-init.sh` — confirm mode `100755`. The whole `add-ralph`
  work item depends on the execute bit surviving in git.

# Appendix

## The six design-review dimensions (step 3b)

Concept compliance, abstraction quality, duplication avoidance, data structure clarity, interface
completeness, implementability. Issues are then sorted Critical / Major / Minor.
Source: `ralph-init.sh:361-457`.

## Spec file structure requested at step 4

Purpose (one sentence), Requirements (behavioral outcomes), Acceptance Criteria (Given/When/Then),
Interfaces, Constraints, Out of Scope. Target 50–150 lines each, ordered foundational-first, one
topic per file — "a distinct capability area that can be described in one sentence without using
'and' to conjoin unrelated things." Source: `ralph-init.sh:579-624`.

## AGENTS.md sections requested at step 5

Build & Run, Validation, Codebase Patterns, Known Gotchas. ~60 lines max, operational only — no
status, no progress, no changelogs. Source: `ralph-init.sh:646-687`.

## The 9s guardrails, verbatim from the build meta-prompt

More 9s means more critical (`ralph-init.sh:775-784`):

```
999:          Capture the why in docs and tests
9999:         Single sources of truth, no migrations/adapters
99999:        Implement completely. No placeholders, no stubs.
999999:       Keep IMPLEMENTATION_PLAN.md current with learnings
9999999:      Update AGENTS.md with operational learnings only, keep brief
99999999:     For bugs found, resolve or document in IMPLEMENTATION_PLAN.md
999999999:    Clean completed items from IMPLEMENTATION_PLAN.md periodically
9999999999:   AGENTS.md is operational only — no status, no progress notes
99999999999:  Don't assume not implemented — always search first
```

## Flags and environment variables

| Flag | Default | Effect |
|---|---|---|
| `--model <m>` | `sonnet` | Steps 4–7 (specs, AGENTS.md, both prompts) |
| `--design-model <m>` | `sonnet` | Steps 3, 3b, 3c only. README suggests opus. |
| `--resume` | off | Skip steps whose output exists and is non-empty; enter existing worktree |
| `--help` | — | Usage |

`RALPH_MODEL` and `RALPH_DESIGN_MODEL` set the same two defaults (`ralph-init.sh:24-25`). Neither
reaches `loop.sh`.

with `scripts` in the directory-creation loop at line 93 and a Ralph usage hint in the post-install
